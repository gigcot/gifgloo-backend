# 설문과 매일 3회 받기

합의: 유입 캠페인과 관계없이 합성 1회 이상 완료하면 선택 설문에 참여한다. 설문 제출 즉시 1회 보상은 유지한다. 기존 설문 완료자와 새 참여자 모두 프로필에서 매일 3회분을 직접 받을 수 있다. 설문 당일에도 받을 수 있어 첫날 추가 지급은 최대 4회다. 회원·비회원 모두 같은 서버 사용자 ID 단위로 처리한다. 한국시간 자정에 새 수령일이 시작되고 각 지급분은 지급 후 7일 유효하며 남은 이용권과 함께 누적된다. 공유·긍정 답변은 지급 조건이 아니다.

## 구현과 검증 기준

- 기존 설문 GET/POST의 캠페인 조건을 제거하고 합성 완료 조건·1회 응답/보상은 유지한다.
- `GET /experiments/exp-001/daily-reward`는 설문 완료자의 수령 상태만 읽는다. `POST`는 3회분을 지급한다. 사용자 ID와 날짜·횟수는 클라이언트 입력을 받지 않는다.
- 응답: `claim_date`(KST 날짜), `claimed`(그날 수령 여부), `granted`(이번 호출에서 새로 지급), `server_now`(상태 판단에 사용한 서버 시각), `next_claim_at`(다음 KST 자정의 UTC 시각), `expires_at`(미수령이면 null). 화면의 자정 재조회는 서버 시각 간 차이로 예약하여 기기 시계 오차가 반복 요청을 만들지 않게 한다.
- 지급은 `DAILY_REWARD` source, `user_id:YYYY-MM-DD` source ID로 저장한다. 계정 행 잠금 뒤 지급 이력을 확인하고 같은 트랜잭션에서 저장한다. 기존 lot/transaction source 유일성 제약을 함께 사용한다. 중복 클릭·응답 유실 재시도는 같은 지급분을 반환하며 만료일도 연장하지 않는다.
- 기존 `EXPERIMENT` 설문 1회 보상·`PAYMENT` 구매와 구분한다. 차감 transaction의 `credit_lot_id`와 합성 job ID로 실제 소비를 연결한다. 기존 만료순 차감·실패 환불을 유지한다.
- 저장 구조 변경은 없다. 새 enum 값을 읽을 수 있는 백엔드를 먼저 반영한 뒤 프론트를 반영한다. 새 지급 후 옛 enum만 읽는 백엔드로 되돌리면 해당 이용권을 읽지 못하므로 호환성을 보존해야 한다.

## 반복 제작 관찰

질문은 “무료 기회가 더 있을 때 계속 만들고 싶어 하는 사용자가 있는가?”다. 혜택 안내 노출 → 설문 → 지급 → 실제 소비·완료 → 이후 제작을 구분한다. 지급 버튼 클릭이나 프로필 방문만으로 제작 가치가 확인됐다고 하지 않는다.

`report.sql`은 설문 제출일로 대상을 정한 뒤, 지급과 차감·환불·합성을 사용자별로 연결하는 읽기 전용 PostgreSQL 쿼리다. 운영 조회는 별도 실행 시 실제 기간·읽기 권한을 확인한다. 연결 문자열은 파일에 저장하지 않는다.

```sh
psql "$ANALYTICS_DATABASE_URL" -v ON_ERROR_STOP=1 \
  -v cohort_start='2026-10-22T00:00:00+09:00' \
  -v cohort_end='2026-10-29T00:00:00+09:00' \
  -v observed_until='2026-11-05T00:00:00+09:00' \
  -v internal_account_ids="$OBSERVATION_INTERNAL_ACCOUNT_IDS" \
  -f analytics/daily-rewards/report.sql
```

날짜는 사용법 예시이며 합의된 관찰 기간이나 성공 기준이 아니다. 기존 설문 완료자도 포함하려면 cohort 시작을 그들의 제출 이전으로 지정한다. 사용자별 경과일을 함께 읽고, 기간이 짧은 신규 참여자를 오래 지켜본 사람과 같은 재방문 비율로 비교하지 않는다. 운영자·QA 계정은 결과에서 제외하고, 익명 사용자 ID 수를 실제 사람 수로 확정하지 않는다.

- `claim_days/granted_uses`: 직접 수령한 날짜 수와 지급량. 미사용 비축일 수 있다.
- `deducted_daily_jobs/refunded_daily_jobs`: 일일 지급 lot에서 차감된 합성과 이후 환불. 지급 직후의 모든 합성을 일일 이용권 사용으로 계산하지 않는다.
- `completed_daily_jobs`: 일일 지급분으로 차감됐고 환불되지 않았으며 현재 완료 상태인 합성.
- `completed_jobs_after_first_claim/production_days_kst`: 첫 수령 이후 접수해 현재 완료된 전체 합성과 접수일 수. 기본·설문·구매 이용권 사용도 포함한다. 같은 날 집중 제작과 다른 날 제작을 모두 본다.
- `first/last_production_at`: 완료 합성의 접수 시각이다. 현재 DB에 별도 완료 시각이 없으므로 완료 시각이라고 부르지 않는다. `observed_until`은 접수·거래 범위를 제한하며 현재 job 상태를 과거 시점으로 복원하지 않는다. 같은 종료 시점의 결과를 보존해 비교한다.

반복 제작이 있으면 기존 평가·결과 저장/공유 시도와 제작 이유를 대조한다. 같은 조합 반복이 불만족 재시도인지, 다른 목적의 제작인지 이벤트만으로 확정하지 않는다. 설문 미참여는 설문 부담이나 안내 누락일 수도 있다. 추가 제작·서버에서 확인한 실제 결제는 서로 다른 근거이며 보상 제공 조건을 붙여 해석한다.

## 클라이언트 관찰 계약

- `survey_reward_offer_viewed`: 결과/내 에셋 안내가 화면에 들어온 경우. 현재 문서 수명 내 사용자·위치별 한 번.
- 기존 `exp001_survey_*`: 진입·시작·제출. 답변/자유문은 분석 이벤트에 넣지 않는다.
- `daily_reward_menu_opened`: 프로필 직접 진입, 설문 완료 안내, 이용권 부족 안내의 source를 구분한다.
- `daily_reward_offer_viewed`: 서버에서 조회한 날짜·수령 상태. 재조회가 포함될 수 있으므로 이벤트 수를 사람 수로 보지 않는다.
- `daily_reward_claim_clicked/confirmed/failed`: 클릭·성공 응답·실패. `confirmed.granted=false`는 중복 요청 확인이며 신규 지급이 아니다. 실패 이벤트도 서버 지급 실패를 증명하지 않는다. 확정 지급량은 DB가 기준이다.
- `pass_exhausted`: 합성 시도에서 서버가 이용권 부족을 반환한 경우. 설문 상태를 함께 기록한다.
- 기존 합성·결과 이벤트는 job ID로 연결한다. 다운로드 시작·공유 응답을 실제 외부 사용으로 단정하지 않는다.

PostHog 보드 15는 신규 수령 확인 → 이후 접수·여러 날 수령을 계정으로 연결한다. `granted=false`와 중복 응답은 신규 지급으로 세지 않는다. 16은 결제 시작·결제창 호출·완료 응답·실패/취소를 계정과 테스트 여부로 나눈다. 주문 ID가 없어 같은 주문의 전환율·결제 건수로 해석하지 않는다. 실제 일일 lot 소비·환불과 결제 원장은 아래 서버 조회로 대조하며 PostHog로 자동 동기화하지 않는다.

## 서버 원장 대조 — 2026-10-23

이미 설정된 `gifgloo` SSH 연결과 운영 컨테이너의 DB 연결을 이용한다. DB 비밀번호·이메일·사용자별 원본을 출력하지 않고 집계만 반환한다. 15초 쿼리 제한과 읽기 전용 트랜잭션을 적용한다. 보고서 조회 자체는 지급·차감·합성·결제를 발생시키지 않는다.

```sh
python3 -B analytics/daily-rewards/read_observation.py \
  --cohort-start '2026-10-20T00:00:00+00:00' \
  --cohort-end '2026-10-23T06:19:32+00:00' \
  --observed-until '2026-10-23T06:19:32+00:00' \
  --internal-account-ids "$OBSERVATION_INTERNAL_ACCOUNT_IDS"
```

시각은 이번 점검의 예시다. 실제 회차에 맞춰 변경한다. `OBSERVATION_INTERNAL_ACCOUNT_IDS`에는 프론트 비공개 PostHog 설정의 제외 계정 목록과 같은 값을 넣는다. 빈 문자열은 운영자 제외 없음이므로 결과의 `excluded_account_count`를 확인한다. 서버 보고서의 일일 혜택 코호트는 **설문 제출일**, 결제는 **주문 생성일**이다. PostHog 15의 **수령 확인일**과 다르므로 코호트를 맞추기 전 두 숫자를 전환율로 나누지 않는다. 오래된 설문 참여자를 포함하려면 제출일 시작을 넓힌다.

`payments.sql`은 주문별 고유 DB 행을 LIVE/TEST/UNKNOWN·현재 상태·통화별로 집계한다. `order_amount`는 해당 상태의 주문 금액 합이며 전체를 매출로 더하지 않는다. 실제 지불 관측은 LIVE + APPROVED를 확인하고 취소·환불 상태를 함께 본다. 후속 상태는 조회 시점 기준이며 과거 상태 복원이 아니다.

이번 운영 읽기 검증(UTC 2026-10-23 06:19:36): gigcot 로그인 계정 두 개 제외 후 설문·일일 수령 계정 1개, 일일 3회분 지급, 일일 lot 차감 합성 4개 중 환불 3개·완료 1개, 수령 뒤 전체 완료 합성 2개, 기간 내 결제 주문 없음. 비회원 합성 기록은 운영자 여부 미확인으로 남겼으며 자연 사용자 가치 검증으로 확정하지 않는다. 차감 4개가 지급 3회보다 많은 것은 실패 환불 뒤 재사용을 포함하기 때문이다.

## 아키텍처·요청 비용 자기 검토 (2026-10-22)

- Experiment 서비스는 설문 참여 자격과 트랜잭션을 담당하고, 전용 bridge port/adapter를 통해 Credit application service를 호출한다. 도메인 서비스가 타 도메인의 DB 모델에 접근하지 않는다. 지급·차감·만료는 기존 Credit aggregate/repository를 사용한다.
- 일일 상태 GET은 설문 1건과 지급 거래 1건을 읽으며, 쓰기나 행 잠금을 수행하지 않는다. 조회 조건에 대응하는 기존 유일성 인덱스를 확인했다. 지급 POST는 해당 사용자 계정과 잔액이 남은 lot를 잠근 뒤 중복 지급을 재확인한다. 외부 API 호출을 포함하지 않고 기존 합성·결제와 잠금 순서를 공유한다.
- 브라우저에서 세 문제를 수정 전 재현했다: 설문 최초 조회 2회, focus/visibility 동시 이벤트의 일일 조회 2회, 기기 시계가 하루 앞섰을 때 3.2초 동안 추가 조회 3회. 진행 중 조회 공유와 `server_now` 기준 타이머로 수정하고 회귀 테스트를 추가했다. 합성 완료 후에는 이전 조회가 진행 중이어도 최신 상태를 별도로 조회한다.
- `report.sql`은 운영자가 별도로 실행하는 분석 쿼리이며 사용자 화면 요청 경로에 연결하지 않았다.
- 로컬 PostgreSQL 16을 실행한 뒤 `credit_account/integration_tests`의 동시 10회 지급·롤백 후 재시도 2개 테스트를 통과했다. 별도 로컬 DB에 전체 마이그레이션을 적용한 실제 FastAPI에서도 비회원 세션 → 완료 샘플 → 설문 1회 지급 → 동시 POST 10회를 검증했다. 모든 지급 요청이 200이고 새 지급은 1건, 일일 lot/CHARGE는 각각 1건, 잔여 이용권은 1→2→5회였다. 운영 데이터에 대한 실행 계획·지연 시간·부하 시험은 수행하지 않았으므로 처리량 보장이나 운영 성능 검증 완료를 뜻하지 않는다.
