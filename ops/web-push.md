# 작업별 완료 알림

이번 알림은 사용자가 대기 화면에서 신청한 합성 1건만 대상으로 한다. 로그인·마케팅 구독을 요구하지 않는다. 합성 완료 트랜잭션은 변경하지 않았고 별도 발송기가 완료 상태를 읽는다.

## 운영 전 설정 (아직 실행하지 않음)

1. 기존 익명 User 마이그레이션 이후 `202610070001`을 검토·적용한다. 운영 적용은 별도 승인 대상이다.
2. `requirements.txt`를 설치한다. 발송은 `pywebpush`를 사용한다.
3. 운영 VAPID 키 쌍을 비밀 관리 저장소에서 설정한다. 생성 도구는 `.venv/bin/python -m tools.generate_web_push_keys`이며 `.env.web-push.local`에 0600 권한으로 저장한다. 기존 파일은 덮어쓰지 않으며 키를 터미널에 출력하지 않는다. `WEB_PUSH_PRIVATE_KEY`는 base64url raw/DER EC P-256 키, `WEB_PUSH_PUBLIC_KEY`는 base64url uncompressed 공개키다. 생성 파일은 Git 제외 대상이고 기본 활성화 값은 false다. 비공개 키는 로그·Git·프론트 환경변수에 넣지 않는다. 공개키만 설정 API로 제공한다. 테스트 키와 운영 키를 구분하고 기존 구독이 있는 운영 키를 임의 교체하지 않는다.
4. `WEB_PUSH_SUBJECT=mailto:운영자연락처`, `WEB_PUSH_ENABLED=true`를 설정한다. 기본값은 false다. 공개·비공개 키 불일치는 시작 시 실패한다.
5. 프론트 HTTPS에서 서비스 워커·manifest 제공, 백엔드 CORS_ORIGINS에 정확한 프론트 origin 등록을 확인한다. 실제 푸시 등록·발송은 이 작업의 테스트에서 실행하지 않는다.

## 계약과 수명

- `GET /web-push/config`: 활성화 여부·공개키만 반환, no-store.
- `POST /compositions/{job_id}/notification`: 현재 사용자 소유 작업 + 브라우저 구독 정보. 동일 작업·수신 주소 반복 신청은 중복 행을 만들지 않는다. 실패 작업은 거부한다.
- `DELETE /compositions/{job_id}/notification`: 현재 사용자의 해당 작업 알림 취소. 이미 푸시 서비스에 접수된 알림을 회수하지는 못한다.
- 작업별 신청 행은 24시간 경과 후 발송기의 다음 정리 실행에서 삭제한다. 발송 성공/영구 실패/취소 시 endpoint·암호화 키는 즉시 비운다. 완료 전에 작업이 실패해도 24시간 이후 정리된다. 발송기 비활성화·장기 중단 시 정리도 멈추므로 기존 구독정보 삭제를 별도로 점검한다.
- 서버 프로세스 내 비동기 발송기는 DB 행을 잠금·선점하고 최대 3회 시도한다. PostgreSQL SKIP LOCKED + 2분 lease로 여러 프로세스·재시작을 처리한다. 전송 타임아웃 10초, 재시도 30/60초, 푸시 서비스 TTL 1시간.
- 취소·실패 후 재신청은 새로운 내부 발송 ID를 사용한다. 이전 발송의 늦은 응답이 재신청 상태를 덮어쓰지 않는다. 같은 작업·수신 주소의 활성 신청은 여전히 한 건이다.
- 네트워크 접수 후 서버가 죽는 경우 정확히 한 번의 전송은 보장할 수 없다. 작업 ID별 notification tag로 브라우저 중복 표시를 줄인다. HTTP 성공은 기기 표시 성공이 아니다.
- 알림에는 사진·공개 에셋 URL·인증 토큰을 넣지 않는다. 클릭하면 기존 소유권 확인을 거치는 `/my-assets?job=...&from=notification`으로 간다. 자동 공개 공유 링크는 만들지 않는다.
- 허용된 Web Push 제공자 HTTPS 호스트만 등록하며 리다이렉트는 따르지 않는다. endpoint·키는 분석 이벤트/발송 오류 로그에 남기지 않는다.

## 별도 실기기 확인

- 데스크톱/Android 지원 브라우저: 허용·거절·탭 닫힘·서버 재시작·중복 신청·클릭 복귀.
- iOS/iPadOS: 홈 화면 웹앱에서만 지원. Safari 세션과 홈 화면 앱의 익명 식별 연속성, 구독 시점과 결과 소유권을 실제 기기에서 검증하기 전 동일성을 보장하지 않는다.
- 쿠키 삭제·기존 회원 로그인으로 주체 변경 후에는 이전 익명 결과 접근을 복구하거나 권한을 우회하지 않는다.
- 개인정보 안내에 선택적 알림 수신 정보·작업별 보관 기간을 반영하는 운영 검토가 남아 있다. 이번 작업이 기존 약관 개정·적법성 검증을 대신하지 않는다.

## 비용 없는 로컬 실기기 확인

백엔드 루트에서 실행한다.

```sh
.venv/bin/python -m tools.web_push_smoke
```

1. 이 컴퓨터의 실제 Chrome 또는 Safari에서 `http://localhost:8766`을 연다. 자동 권한 요청·자동 발송은 없다.
2. `알림 허용하고 1회 테스트`를 직접 누르고 브라우저 권한을 선택한다. 허용하면 실제 Web Push 서비스에 1회 전송한다. 거절하면 전송하지 않는다.
3. 8초 뒤 알림 센터 수신과 클릭 후 테스트 결과 페이지 복귀를 확인한다. 탭을 닫는 것은 수신 조건이 아니다. 탭을 닫아도 수신하는지 추가로 확인할 때만 접수 안내 이후 탭을 닫고 브라우저 앱은 실행해 둔다. macOS 사이트 알림·OS 알림·집중 모드도 구분한다.
4. 복귀 페이지에서 테스트 구독 정리 링크를 눌러 정리한다. 사이트 알림 권한은 브라우저 설정에서 해제하고 터미널 서버는 Ctrl+C로 종료한다.

이 도구는 메모리에서 테스트 VAPID 키·구독을 사용한다. `.env`, DB, 스토리지, OAuth, 실제 합성을 읽거나 호출하지 않는다. 실행마다 새 키이므로 그 테스트 origin의 기존 구독은 버튼 클릭 시 교체한다. 키·구독은 로그에 출력하지 않는다. localhost 전용 Host/Origin·세션·CSRF 검사와 1회 제한이 있다. 테스트 중에는 localhost:8766을 다른 작업에 사용하지 않는다.

실제 제품의 발송 어댑터와 서비스 워커를 재사용하지만 **운영 인증·합성 완료 이벤트·실제 내 결과 데이터까지 연결한 종단 검증은 아니다**. 모바일은 이 localhost에 접근할 수 없으며 iOS 홈 화면 앱/HTTPS 검증은 따로 필요하다. 발송 서비스의 accepted는 기기 수신 성공과 다르다.

## 자동 검증

단위/API·설정·로컬 테스트 도구 검증: `.venv/bin/python -m unittest discover -s composition/unit_tests`

PostgreSQL 알림 테스트는 명시적인 빈 임시 DB만 허용한다. 기존 DB를 초기화하지 않는다.

```sh
PUSH_TEST_DATABASE_URL=postgresql://gifgloo_verify:local_verify_only@127.0.0.1:55433/gifgloo_push_verify .venv/bin/python -m unittest discover -s composition/integration_tests -v
```

2026-10-08: 알림·설정 20개, 기존 API 27개, User 27개, Experiment 22개, Credit 8개 통과. 별도 tmpfs PostgreSQL 16에서 알림 10개 및 익명 User 7개 통과. 신규 알림 migration의 upgrade/downgrade/재upgrade, 기존 작업 보존, 8개 동시 신청·선점, 실제 SKIP LOCKED, lease 복구·늦은 응답, 재신청 세대 분리, 만료 정리를 확인했다. 자동 테스트의 푸시 네트워크는 모의 전송으로 대체했다. 운영 키 생성·운영 DB 적용은 아직 실행하지 않았다.

별도 로컬 실기기 시험(2026-10-08): 사용자가 직접 권한 허용·발송을 실행했다. 서버 accepted 로그와 사용자 보고로 macOS 알림 센터 수신 및 알림 클릭 후 ‘알림 클릭 복귀 확인’ 페이지 도착을 확인했다. 탭을 열어둔 상태에서도 수신했다. 배너가 눈에 보이지 않았던 구체적인 OS 설정 원인은 확정하지 않았다. 실제 합성·운영 데이터 없이 실행한 전송/복귀 검증이며, 탭·브라우저 완전 종료 상태와 Safari/iOS 전반 및 실제 제품의 종단 검증은 별도다.
